# Отчёт: масштабируемость D-Galois по числу узлов

## 1. Введение

**Задача:** оценить, как распределённый графовый
движок [D-Galois](https://github.com/IntelligentSoftwareSystems/Galois/tree/master/lonestar/analytics/distributed)
масштабируется с ростом числа MPI-процессов на 4 классических задачах распределённого анализа графов:

- **BFS** — Breadth-First Search
- **SSSP** — Single-Source Shortest Path
- **PR** — PageRank
- **TC** — Triangle Counting

**Особенность нашего эксперимента:** мы запускаем D-Galois локально (без настоящего кластера), эмулируя «узлы»
отдельными MPI-процессами на одной машине. Это позволяет увидеть характер масштабирования платформы, но абсолютные числа
стоит интерпретировать с учётом ограничений, описанных в разделе 7.

> **Почему два графа:** TC требует строго симметричного графа без self/multi-edges (assertion в `MiningPartitioner.h`).
> Прямая симметризация LiveJournal искажает его свойства, поэтому для TC выбран com-Orkut — изначально неориентированный
> граф социальных сообществ. Это означает, что *абсолютное* время TC нельзя сравнивать с другими алгоритмами, но
*speedup* — корректно.

## 4. Методология

| Параметр                     | Значение                                         |
|------------------------------|--------------------------------------------------|
| Число MPI-процессов **N**    | {1, 2, 4, 8}                                     |
| Потоков на процесс `-t`      | `max(1, ⌊nproc/N⌋ − 1)` → 11/5/2/1               |
| Партиционирование            | `oec` (Outgoing Edge-Cut)                        |
| Тип связи                    | `Sync` (Bulk-Synchronous Parallel)               |
| Повторов на конфигурацию     | 3, метрика — медиана                             |
| `GALOIS_DO_NOT_BIND_THREADS` | `1` (обязательно при N процессах на одном хосте) |

**Метрики:**

- **T(N)** — медиана времени вычислительной фазы (`Timer_<run>` из statFile, миллисекунды).
- **Speedup** S(N) = T(1) / T(N).
- **Efficiency** E(N) = S(N) / N. 1.0 — идеальное масштабирование.

Полный дизайн — в [`experiments/design.md`](design.md).

## 6. Интерпретация

### Что увидели

1. **Все 4 алгоритма масштабируются до N=4, потом деградируют.** Speedup max достигается на N=4 для всех задач (1.51× —
   3.35×).

2. **Ранжирование по качеству масштабирования:** TC (3.35×) > PR (3.25×) > SSSP (2.18×) > BFS (1.51×).

3. **TC и PR показали лучшую эффективность при N=2 и N=4** (0.94 и 0.81 соответственно): эти алгоритмы **compute-bound**
   или с регулярной нагрузкой, и накладные расходы на партиционирование/коммуникацию маленькие относительно полезной
   работы.

4. **BFS — самое слабое масштабирование (1.51× max).** На LiveJournal BFS отрабатывает за 1.3 секунды на одном
   процессе — это слишком быстро, чтобы выгода от параллелизма перекрыла накладные расходы на инициализацию Gluon, edge
   inspection и обмен сообщениями.

5. **При N=8 — деградация у всех.** Время в 1.5–2× больше, чем при N=4. Это критическая черта single-node эмуляции (см.
   раздел 7).

### Почему BFS масштабируется хуже всех

BFS на LiveJournal обходит ≈ 4.4M узлов из 4.85M за 9 итераций (`NumIterations_*=9` в CSV). При N процессов:

- инициализация графа (CuSP, partition) занимает фиксированное время ~3 секунды (`GraphConstructTime, HMAX, 3084` ms),
- каждая BFS-итерация требует синхронизации между процессами (Gluon reduce),
- сама фаза BFS — всего ~1.35 секунды на одном процессе.

Соотношение «коммуникация / вычисление» для BFS высокое, поэтому распределение урезает выигрыш. Это типичная картина для
frontier-based алгоритмов на средних графах в литературе по Gluon.

### Почему PR и TC масштабируются лучше

- **PR** — каждая итерация трогает все рёбра графа и делает ровно один reduce на узел. Объём работы на процесс
  предсказуемый, нагрузка балансируется хорошо, и при N=4 видно speedup 3.25× (efficiency 0.81 — близко к идеалу).

- **TC** — compute-bound (для каждой пары рёбер ищем общих соседей), коммуникации между раундами минимальны. На больших
  графах (com-Orkut, 117M рёбер) полезной работы много, накладные расходы пренебрежимы. Speedup 3.35× при N=4,
  efficiency 0.84.

### Почему при N=8 всё падает

`nproc=12`, при N=8 на каждый процесс отводится `t = ⌊12/8⌋ − 1 = 0 → 1` поток (после клампа). Реальное число активных
потоков на хосте: 8 процессов × (1 рабочий + 1 communication-thread) ≈ 16, что превышает 12 ядер. Это **oversubscribe**:
переключения контекста Linux-планировщиком, конкуренция за L3-cache и RAM-bandwidth, рост latency MPI-барьеров. Это и
видно как замедление в 1.5–2×.

## 7. Ограничения single-node эмуляции

Этот эксперимент не моделирует настоящий кластер. Главные искажения:

1. **Все процессы делят общую RAM и шину памяти.** Нет независимых memory channels на узел, как в кластере. При большом
   N полоса памяти становится узким местом.
2. **«Сетевая» коммуникация идёт через shared memory** (Open MPI auto-detect). Это **быстрее**, чем настоящая сеть (≪10
   µs vs 10–100 µs latency на InfiniBand/Ethernet) — поэтому накладные расходы коммуникации в нашем эксперименте *
   *занижены**.
3. **NUMA не отражает реальный кластер.** На i5-11400H одна NUMA-нода, в кластере — несколько с разной задержкой.
4. **При N > nproc/t — oversubscribe.** В нашем случае N=8 уже близок к границе.
5. **Один прогон длиной 1 час — недостаточно для статистики флактуаций.** При большем числе run-ов (5–7) можно было бы
   увидеть доверительные интервалы.

**Что это значит для интерпретации:**

- Видимая «деградация при N=8» — частично артефакт single-node, в реальном 8-узловом кластере её бы не было.
- Видимая «эффективность 0.94 при N=2 для TC» — оптимистическая оценка, в кластере с реальной сетью эффективность была
  бы меньше из-за более дорогой коммуникации.
- **Ранжирование алгоритмов** (TC > PR > SSSP > BFS по качеству масштабирования) — устойчивая характеристика, которая
  останется и в кластере.

## 8. Выводы

1. **D-Galois даёт измеримый параллельный speedup** на всех 4 классах задач, максимум 3.35× при N=4 на машине с 12
   логическими ядрами.

2. **Compute-bound задачи (TC, PR) масштабируются лучше**, чем frontier-based (BFS, SSSP). Это согласуется с теорией и
   публикациями.

3. **Sweet spot — N=4** для нашей конфигурации. N=8 даёт oversubscribe и регрессию.

4. **На малых задачах (BFS на LJ за ~1.3s) распределение почти не имеет смысла** — накладные расходы Gluon (~3s
   GraphConstructTime + per-round sync) сравнимы с самим вычислением.

5. **Эксперимент воспроизводим**: см. README, scripts/01-..05-, фиксированный commit Galois.
